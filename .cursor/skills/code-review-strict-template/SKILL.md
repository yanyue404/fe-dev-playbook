# 代码评审严格模板

## 触发条件

当用户明确提出评审相关请求时启用本技能，例如：
- code review
- PR review
- merge request review
- review this change
- assess quality before merge

若仅是实现需求且未要求评审，不启用本技能。

## 核心目标

输出以风险为中心的评审，优先发现可执行的问题：
1. 正确性缺陷
2. 行为回归风险
3. 安全或数据完整性风险
4. 测试缺失或覆盖不足

## 评审流程

1. 从 Git 收集变更上下文：
   - `git status`
   - `git diff`（包含 staged + unstaged）
   - `git log --oneline -n 20`
2. 检查所有改动文件，不只看最近一次提交。
3. 结合运行场景与边界条件验证行为。
4. 检查测试：
   - 已有测试是否受改动影响
   - 新增/变更行为是否缺少测试
5. 按下方“严格输出模板”给出结论。

## 严重级别规则

- `Critical`：可能导致错误结果、崩溃、数据丢失、安全问题或阻塞发布。
- `Major`：高概率缺陷/回归，或明显的可维护性风险。
- `Minor`：非阻塞问题，但对可读性/性能/风格有实际影响。

避免夸大级别；若不确定，降低级别并明确假设。

## 严格输出模板

输出必须严格遵循以下章节顺序：

```markdown
## 发现的问题

### [级别] 问题标题
- File: `path/to/file`
- Issue: 问题是什么，以及为什么重要。
- Evidence: 具体代码行为、复现场景或 diff 证据。
- Fix: 明确可执行的修复建议。
- Test: 需要新增或更新的测试。

（每个问题一个块，按严重级别从高到低排序）

## 开放问题 / 假设
- 列出会影响正确性的未确认点；若无，写 `无`。

## 变更概览
- 用 2-4 条要点概述改动内容。

## 剩余风险
- 说明在建议修复后仍然存在的风险。
- 若未发现问题，也要写测试盲区或结论置信度限制。
```

## 无问题时的写法

即使未发现问题，也必须输出所有章节，并满足：
- `## 发现的问题` 下写：`未发现阻塞性问题。`
- 除非已有测试完整验证，否则仍需给出至少一条“剩余风险”或“测试缺口”。

## 写作约束

- 问题描述必须具体、可复现。
- 优先给出行为层证据，不给空泛建议。
- 不扩展到无关架构改造。
- 在“发现的问题”前不要先写夸赞性内容。
- 术语保持一致：统一使用“问题”“风险”“测试缺口”。
