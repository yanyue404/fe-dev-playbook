# 前端开发需求分析与执行

## 核心原则

**在用户明确同意之前，绝不动手改代码。**

所有修改必须遵循以下铁律：

- 不大规模重构
- 不引入不必要依赖
- 不拍脑袋修改——每个改动必须有依据
- 不引入新的回归问题
- 必须明确问题根因
- 在必要位置补充日志
- 修改范围最小化
- 不顺手重构或格式化无关代码
- 尽量复用现有组件和状态管理方式

---

## 工作流程

### 阶段一：需求接收与分析

1. **接收输入**：用户提供 Word、PDF、Markdown 文件、消息文本或截图
   - 若输入为 Word/PDF，优先使用微软 `markitdown` 转为 Markdown 后再分析
   - 转换命令示例：`markitdown "input.docx" -o "output.md"` / `markitdown "input.pdf" -o "output.md"`
   - 若输出中出现 `![](data:image/...base64...)` 占位格式，必须提取原文档图片为本地文件并替换为相对路径（如 `![](images/image_01.png)`），确保 Markdown 可直接预览图片
   - 解析时重点关注图片相关信息（图片说明、OCR 文本、图表关键信息、截图中的文案）
   - 若图片信息缺失或不完整，需在分析结论中明确标注“图片信息提取受限”
2. **理解需求**：
   - 提取关键功能点和验收标准
   - 识别涉及的页面、组件、接口
   - 标记不明确或有歧义的地方
3. **探查现有代码**：
   - 定位相关文件和组件
   - 了解现有的状态管理方式（Vuex/Pinia/React Context 等）
   - 了解现有的 UI 组件库和工具函数
   - 检查是否有可复用的逻辑

### 阶段二：任务计划制定

向用户输出结构化的任务计划，格式如下：

```
## 需求分析结果

### 需求概述
[一句话描述核心需求]

### 影响范围
- 涉及文件：[列出将修改的文件]
- 涉及组件：[列出受影响的组件]
- 涉及接口：[如有接口变更]

### 根因分析（如为 bug 修复）
- 问题现象：[描述]
- 根本原因：[分析]
- 验证方式：[如何确认根因]

### 执行计划
1. [ ] 步骤一：[具体改动描述] — 文件：`xxx.vue`
2. [ ] 步骤二：[具体改动描述] — 文件：`xxx.ts`
...

### 不做的事情
- [明确排除哪些改动，避免范围蔓延]

### 风险点
- [潜在的回归风险及应对措施]
```

**等待用户确认后才进入下一阶段。**

### 阶段三：反复确认（如有必要）

如果用户有疑问或修改意见：
- 逐条回应，调整计划
- 重新输出更新后的计划
- 再次等待确认

**只有用户明确表示"开始"/"确认"/"可以"等肯定答复后才开始执行。**

### 阶段四：逐步执行

1. 按照确认后的计划，逐步执行每一项改动
2. 每完成一步，使用 TodoWrite 标记进度
3. 每个改动后检查 linter 错误（ReadLints）
4. 在关键逻辑处补充必要的 `console.log` / `console.warn` 日志
5. 执行完毕后汇总改动清单

### 阶段五：改动总结

输出最终改动报告：

```
## 改动总结

### 已完成
- [x] 步骤一：[描述] — `文件路径`
- [x] 步骤二：[描述] — `文件路径`

### 修改文件清单
| 文件 | 改动类型 | 说明 |
|------|----------|------|
| xxx.vue | 修改 | ... |

### 新增日志点
- `文件:行号` — 日志内容及用途

### 验证建议
1. [用户可执行的验证步骤]
2. [回归测试关注点]
```

## 改动守则（执行阶段必须遵守）

### 必须做

- 改动前先读取目标文件，理解上下文
- 复用项目中已有的组件、hooks、工具函数
- 保持与现有代码风格一致
- 在不确定的地方添加防御性日志
- 修改后立即检查 linter

### 禁止做

- 改与需求无关的代码
- 升级或新增依赖包（除非需求明确要求）
- 重命名或移动与需求无关的文件
- 格式化不在改动范围内的代码
- 删除现有注释或日志（除非是需求要求的清理）
- 在未确认根因的情况下"试着改改看"

## 处理特殊场景

### 收到截图/图片

1. 仔细观察 UI 细节（布局、颜色、间距、文字）
2. 与用户确认：这是期望效果还是当前问题截图？
3. 如果是 bug 截图，追问复现路径

### 收到 Word/PDF 文档

1. 先用 `markitdown` 将文档转换为 Markdown，再进入需求分析
2. 优先提取：标题层级、需求条目、验收标准、接口字段、时间节点
3. 重点核查图片内容：图片标题、截图文案、流程图节点、表格截图中的关键数值
4. 如果转换结果中图片仅保留占位符或缺少 OCR 文本，必须单独提示风险并向用户确认是否需要补充原图说明
5. 交付前检查 Markdown 中所有图片链接可访问（相对路径有效，IDE 预览可见）

### 需求模糊

- 列出不明确的点，逐一向用户提问
- 不做假设，不自行脑补需求
- 用选择题形式帮助用户快速澄清

### 发现需要重构才能实现

- 明确告知用户："当前代码结构需要调整才能优雅实现此需求"
- 提供最小改动方案和重构方案两种选择
- 让用户决定走哪条路
